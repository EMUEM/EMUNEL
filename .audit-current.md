# EMUNEL Current-State Audit

**Audit target:** tracked implementation at commit `a60a863759e81e45e41078dbafdb913db609dfd1` (2026-09-19)  
**Author:** Manus AI  
**Scope:** Every tracked non-generated source and configuration file was inspected. This review treats the repository contents as authoritative and uses the README only to identify claims that were checked against the tree and code. Product source was not changed.

## Conclusion

**EMUNEL is an incomplete scaffold, not a deployable proxy-management platform.** The only complete executable slice is a small raw-TCP proxy core, but it has a critical authentication failure: its VLESS path accepts an arbitrary, unregistered UUID and relays to arbitrary destinations. The FastAPI application cannot import because tracked internal modules and routers are absent. There is no tracked frontend, worker, Compose stack, migration system, test suite, or production deployment definition.

The immediate operational conclusion is **do not expose or deploy this repository**, especially not with the Core listener reachable from untrusted networks. A live local verification connected through the Core with a newly generated UUID that was never registered, reached a controlled echo server, and received the payload back. That is an unauthenticated open-proxy execution path, not merely a theoretical code concern.

## What currently works

### Data model definition and isolated schema creation

The API declares four SQLAlchemy models and `init_db()` imports them before invoking `Base.metadata.create_all()`. In an isolated SQLite audit database, this routine completed successfully. This demonstrates that the model metadata is internally importable and SQLite DDL can be created in isolation; it does **not** demonstrate that the API server or its endpoints work.

The database model is as follows:

| Table/model | Actual stored fields and relationships | Functional limitation |
|---|---|---|
| `users` | UUID-like string primary key; unique username and optional unique email; password hash; enum role (`admin`, `user`, `viewer`); enabled/verified flags; login and timestamps. It relates to subscriptions and audit logs. | There is no bootstrap path that creates the configured administrator, no verified-email workflow, no reset/revocation/session model, and no key model. |
| `nodes` | Address, port, unvalidated protocol string, enable/status flags, performance/traffic counters, JSON config/tags, and plaintext `worker_token`. | No node-to-core or node-to-subscription relation, heartbeat endpoint, encrypted secret storage, allocation scheduler, or worker interaction exists. |
| `subscriptions` | User foreign key, traffic and day limits, expiry, auto flags, device counts, active state, reset day, notification flag, and `link_token`. It exposes computed quota properties. | It is not linked to a proxy credential, a node, a device/session, or a public subscription-feed endpoint. No code performs automatic reset, renewal, expiry disabling, notification, or device enforcement. |
| `audit_logs` | Optional user foreign key, action/resource/detail/JSON metadata/client information and timestamp. | It is never written by the tracked route code, so analytics activity is expected to be empty. |

### Partial CRUD logic, conditional on restoring missing imports

The route bodies express a conventional intended surface: registration/login/token refresh/current user/API-key generation; admin user and node CRUD; subscription CRUD and traffic reset; node/user traffic summaries; and basic platform counts/recent audit activity. Access checks are declared on most management paths, with admin-only mutation for nodes, users, and subscriptions. Non-admin subscription and user-traffic views are scoped to the current user in the route bodies.

These are **unreachable intentions rather than working API behavior**. See the next section for why the application cannot be assembled. Even if the missing modules were supplied, the route code has the correctness and security defects described below.

### Core mechanics that execute

`ProxyServer.start()` can create an `asyncio.start_server` listener. Its TLS context loads a configured certificate/key, enforces TLS 1.2 minimum when configured, and otherwise explicitly starts plaintext. The server can parse a complete VLESS TCP request received in a convenient single read, open a TCP connection to the requested destination, return the VLESS response prefix, and relay bytes bidirectionally. The VLESS verification described in “Core protocol behavior” exercised that narrow mechanics path.

`LinkManager` can format VLESS, Trojan, Shadowsocks, and Base64 multi-link strings. `ConnectionState` can track in-memory connections while they remain open. `PluginRegistry` can register and find a plugin in memory. None of these facilities is connected to persisted subscriptions, API endpoints, client authentication, or plugin discovery.

## Broken implementation paths

### The root service fails immediately

The concrete path is:

```text
python main.py
  -> main.main()
  -> import api.emunel_api.main
  -> from .middleware.auth import AuthMiddleware
  -> ModuleNotFoundError: No module named 'api.emunel_api.middleware'
```

The tracked tree contains no `api/emunel_api/middleware/` directory. Supplying only that module would not make the API work: `routers/v1/__init__.py` also imports untracked `network_tests`, `logs`, and `settings` router modules, while every visible router imports untracked `services.auth`. Thus `AuthMiddleware`, JWT/password helpers, `get_current_user`, `require_admin`, `create_api_key`, and the advertised diagnostic/log/settings routes do not exist in the audited source.

The root `main.py` also does not start a Core or Worker despite its docstring saying it runs them in a unified process. It imports only the API and calls `uvicorn.run`. In its present state it cannot reach that call.

### Every advertised API endpoint is blocked by composition failures

`api/emunel_api/main.py` imports and registers routers before the FastAPI object can be used. The earliest missing middleware import blocks all startup. After that is corrected, the missing router imports block startup; after those are corrected, visible endpoints import missing authentication services. Therefore `/`, `/health`, `/api/docs`, and all `/api/v1/*` routes are currently unavailable from the repository as checked.

`init_db()` separately works because it imports models directly rather than the app. It is insufficient as a deployment check because it does not load middleware, routers, or auth services.

## Core protocol behavior and security defects

### Critical: VLESS accepts arbitrary credentials and becomes an open proxy

The effective VLESS execution path is:

```text
TCP connection
  -> ProxyServer._handle_connection(): reads 2 bytes and classifies byte 0 == 0x00 as VLESS
  -> vless.handle(): parses the next 16 bytes as a UUID
  -> QuotaManager.check(uuid): unknown cache entry returns allowed=True
  -> asyncio.open_connection(client-supplied destination)
  -> _relay_tcp(): relays both directions
```

There is no credential store lookup, no association between parsed VLESS UUID and a `User` or `Subscription`, and no quota cache population from the database. `QuotaManager.check()` explicitly permits every user absent from its process-local cache. The audit sent a syntactically valid VLESS TCP request carrying a random, unregistered UUID to the Core and received both the VLESS success prefix `b'\x00\x00'` and an echoed controlled payload. This establishes that the issue is executable.

The same architecture gives unauthenticated callers arbitrary egress capability toward internal or external addresses. It enables SSRF-style access to reachable private services, traffic laundering, scanning, and resource abuse. There is no network egress policy, destination allow/deny list, per-user connection limit, global connection limit enforcement, or meaningful rate limit.

### Trojan and Shadowsocks do not authenticate correctly

Trojan parses a 56-character SHA-224-looking prefix but never validates it against configured credentials. It uses that supplied hash merely as the quota key; absent cache entries are allowed. Any attacker that forms a syntactically sufficient Trojan header can request an outbound TCP connection.

The Shadowsocks handler labels itself a simplified implementation and then treats bytes from an AEAD connection as a plaintext SOCKS-style destination header. It does not derive session keys, decrypt AEAD records, validate authentication tags, parse standard Shadowsocks framing, or establish user identity. Its hard-coded identity is `"ss-user"`. It cannot interoperate correctly with an ordinary encrypted Shadowsocks AEAD client and must not be described as a production Shadowsocks implementation.

### Transport framing and protocol implementation are incomplete

All handlers read the first two bytes, then call a single `reader.read(buffer_size)` to obtain the rest of a handshake. TCP can split or coalesce data arbitrarily; a non-empty `read()` is not a “full header” read. Fragmented valid handshakes can be rejected, while extra data is conflated with header/payload. Proper incremental framing with bounded `readexactly`/buffer parsing is absent.

The protocol detector is heuristic rather than an authenticated parser. It recognizes any first byte from ASCII `0` through `f` as Trojan, which includes non-hex punctuation. Anything not classified as VLESS or that broad Trojan range defaults to Shadowsocks. Plugins are never registered or loaded, so the fallback registry does nothing.

VLESS UDP is explicitly implemented by reusing a TCP connection, so it is not UDP relay behavior. Trojan supports only TCP `CONNECT`; `UDP_ASSOCIATE` is declared but unsupported. There is no server-side WebSocket listener although the generated VLESS links default to `type=ws`; the generated links therefore advertise a transport the raw TCP listener does not provide. Link generation is cosmetic and unbound to actual node/client credentials.

### Quotas, counters, and connection limits are not enforcement

The core’s quota cache is process-local, initially empty, unbounded by eviction policy, and never populated from the API database. Consumption increments only cached identities that already exist, never persists to `subscriptions.traffic_used_bytes`, and does not re-check the cap while forwarding. A client can exceed the remaining quota after its initial check.

`CoreConfig.max_connections` is read but never used to admit or reject connections. `ConnectionState` is also not integrated into relay traffic: the Core registers a connection but never sets its protocol/user or updates bytes. Its aggregate byte statistics cover only still-open connections and vanish on disconnect. Node database counters and the API analytics/traffic results have no input path from the Core, so their apparent metrics will remain initial/default data unless manipulated out of band.

### TLS and operational hardening are unsafe by default

When `CORE_TLS_CERT` and `CORE_TLS_KEY` are absent, the Core logs a warning and listens without TLS. The core configuration defaults to port 443, which makes plaintext proxy operation particularly easy to misconfigure. It has no certificate provisioning, rotation, OCSP, SNI routing, reverse-proxy configuration, or readiness/management API. Relay streams have no idle timeout after handshake and no byte, connection, or task backpressure beyond `writer.drain()`, so slow clients and long-lived tunnels can consume resources.

The Core Dockerfile runs the Python process as the image default user, supplies no health check, no non-root `USER`, no read-only filesystem, no volume/state policy, and no deployment orchestration. It installs only `cryptography`, although the visible Core code does not use it to implement the claimed encrypted Shadowsocks protocol.

## API/database correctness and security concerns

### Configuration makes insecure operation the default

`Settings` defaults both the general and JWT secrets to literal `change-me` values, defaults an administrator username/password to `admin`/`change-me`, defaults CORS to `[*]`, defaults a 24-hour JWT life, and defaults SQLite in the working directory. Startup contains no validation that rejects placeholders, production SQLite, wildcard CORS, weak secrets, or absent worker credentials. The configured `admin_username` and `admin_password` are never consumed to create an account.

The API configuration declares metrics and rate-limiting settings, but there is no metrics endpoint/Prometheus registry or rate-limiting middleware in the tracked source. `.env.example` declares Core, Worker, Dashboard, and Prometheus values that have no corresponding Worker, dashboard, Prometheus, or operational service implementation. These are placeholders, not runtime capability.

CORS is configured as wildcard origins with credentials enabled. This combination is unsafe as a broad policy and is incompatible with browser credentialed wildcard handling; it must be replaced by an explicit deployment-origin allowlist before a browser-facing service exists.

### Authentication and API keys are missing, not merely incomplete

The routes expect `services.auth`, but that directory is absent. Consequently there is no auditable password hashing, token encoding/verification, bearer parsing, API-key persistence, token revocation, refresh rotation, or role enforcement implementation. `POST /auth/api-key` would return an ephemeral value from a missing helper even by its visible route signature; there is no API-key table or hashed-key storage in the model set.

The route layer also lacks login/register throttling, account-lockout policy, audit logging, CSRF/cookie strategy (if a dashboard is later introduced), trusted-proxy/client-IP policy, and a documented separation of public, user, administrator, Core, and Worker credentials.

### Model and CRUD defects

Traffic byte columns use SQLAlchemy `Integer`. On PostgreSQL this is a 32-bit integer, which overflows at approximately 2 GiB—far below a normal subscription quota. `Subscription.traffic_used_bytes`, `Node.total_bytes_up`, and `Node.total_bytes_down` need 64-bit counters and migration coverage.

Model timestamps are naïve `DateTime` values while application comparisons use naïve `datetime.utcnow()`. This invites ambiguous persistence and reporting across time zones. There is no schema migration system, schema version, rollback path, or startup compatibility check; `create_all()` only creates absent tables and cannot safely evolve existing databases.

SQLite’s foreign-key enforcement is not explicitly enabled, so the declared `ondelete` semantics cannot be relied upon in the documented SQLite development mode. `Node.worker_token` is stored as a nullable plaintext column. Subscription link tokens are exposed in every ordinary subscription response, but there is no public consumer or rotation/revocation endpoint.

Data validation is uneven. Creation accepts arbitrary node `protocol` strings and arbitrary address/config JSON. `NodeUpdate` omits lower/upper bounds on port and connection counts that exist in `NodeCreate`. Invalid enum strings in filters or updates (`UserRole(role)`, `NodeStatus(status)`) are not translated into controlled 422/400 responses and can surface as server errors. Email uniqueness is not checked on registration or update; database conflicts are not handled and can become 500 responses. Subscription updates do not provide a clear way to reset an expiry by setting `days_limit` to null, and neither automatic expiry nor `auto_disable` is processed by any background task.

The `AuditLog` model exists but no visible endpoint writes it. Analytics “recent activity” is therefore structurally disconnected from CRUD/auth actions. Analytics and traffic totals query mutable node/subscription counters rather than immutable usage events; there is no time-series table, roll-up job, reconciliation, or transactional accounting path.

## Architecture gap compared with the tracked Lunel reference

The local `lunel-reference` repository is materially more complete in component boundaries and executable integration. This is a comparative inventory, not an assertion that Lunel is defect-free.

| Capability | Lunel reference implementation | EMUNEL current implementation |
|---|---|---|
| Console/frontend | Console ASGI app serves a tracked frontend, mounts assets, provides health/readiness/version endpoints, and separates SPA fallback from API/gateway paths. | No frontend files or static mount; FastAPI app cannot import. |
| Worker plane | Worker exposes authenticated instance launch/stop/restart/remove/status/log/proxy/metrics APIs, heartbeat reporting, and drivers. | No Worker directory, endpoint, driver, heartbeat, node call, or deployment controller. |
| Instance isolation | Docker driver applies CPU/memory/PID limits, drops capabilities, enables no-new-privileges, uses a read-only filesystem/non-root user/private bridge; development process driver applies resource limits. | Single bare Core listener; Core Dockerfile lacks runtime hardening and there is no instance manager. |
| Core management and persistence | Core exposes guarded management APIs for links, stats, connections, logs, metrics, and state flush; it persists state. | Raw TCP Core has no management API, credential store, runtime persistence, or API/DB synchronization. |
| Proxy transports | Tracks WebSocket VLESS/Trojan/Shadowsocks paths, xHTTP routes, and runtime/test integration. | Raw TCP parsers only; WS links are generated but unsupported; UDP and Shadowsocks are incomplete. |
| Deployability | Tracks Dockerfiles for console/worker, Compose with Postgres healthcheck and mandatory secret interpolation, plus optional Caddy edge configuration. | Only a Core Dockerfile; no deployment topology, reverse proxy, database service, secret validation, or operational docs. |
| Validation | Tracks fixtures plus protocol, stream-relay, HTTP, subscription, backup, VMess runtime, and local E2E tests. | No tests. |

Lunel’s architecture shows the components EMUNEL would need to add or consciously replace: a browser console, separate control/data planes, authenticated Core management, Worker/driver lifecycle control, durable state and migrations, public subscription delivery, an edge/TLS design, deployment manifests, and integration tests. Merely copying those files would not be a safe remedy; EMUNEL needs a coherent credential and data model connecting users, subscriptions, link credentials, nodes, workers, and traffic accounting.

## Priority remediation plan

1. **Block deployment and network exposure now.** Do not bind the Core to public interfaces. If any placeholder secrets or exposed listener have already been used, rotate them. Treat the demonstrated arbitrary-UUID relay as a critical security incident condition.

2. **Make a deliberate architecture decision before feature work.** Define the control plane, Worker plane, Core management plane, public subscription endpoint, credential format, and data flows. Implement the missing API modules only after agreeing how subscriptions map to Core credentials/nodes and how traffic returns transactionally.

3. **Do not ship the current protocol engine as a security boundary.** Either use maintained, protocol-conformant proxy runtimes behind an authenticated controller or perform protocol-specific implementation and interoperability work. At minimum, enforce credentials against a durable source before opening an outbound socket; securely authenticate Trojan/SS; implement framing correctly; remove false WS/UDP claims; use strict egress policy; enforce connection/idle/byte limits; and account traffic durably and atomically.

4. **Restore an importable, testable API baseline.** Add the missing `middleware`, `services`, and referenced routers, or remove their imports and claims. Use hardened password hashing and constant-time token/key verification; store only hashed API keys; add token expiry/revocation/rotation; validate production configuration; use explicit CORS origins; throttle authentication; and write audit events.

5. **Make persistence production-safe.** Introduce Alembic migrations, connection/transaction configuration, explicit timezone-aware timestamps, `BIGINT` byte counters, controlled enum/value validation, duplicate/conflict handling, encrypted or external secret storage, and an immutable usage/event model. Add scheduled processing only where it is durable, idempotent, observable, and tested.

6. **Build deployability as actual tracked artifacts.** Add a console/frontend if one is intended; a separate Worker with authenticated heartbeat and lifecycle APIs; hardened Core/worker images; a Compose/Kubernetes deployment; database/reverse-proxy/TLS topology; health/readiness checks; backups; structured logs; metrics; and secret injection without defaults that can reach production.

7. **Establish a test gate before declaring feature support.** Cover startup/import composition, authentication and authorization, CRUD validation/transaction failures, migrations, link issuance/revocation, quota races, actual VLESS/Trojan/Shadowsocks interoperability, fragmented headers, UDP behavior, TLS, egress controls, worker integration, and end-to-end deployment. Add CI that runs these checks from a clean environment.
